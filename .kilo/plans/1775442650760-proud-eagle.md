# Plan: Mejoras para SoleSigner API (`src/api/mod.rs`)

## Resumen del Proyecto
SoleSigner es un sistema de votación digital seguro que garantiza privacidad, auditabilidad y prevención de fraude mediante:
- **Nullifiers** para anonimato (SHA256(documento + salt))
- **Árboles de Merkle** para verificabilidad de votos
- **Validación de identidad biométrica** (selfie + documento vía ONNX)
- **Autenticación JWT** para administradores
- **Estado de elecciones** (DRAFT, OPEN, SEALED) con cierre automático

El archivo `src/api/mod.rs` (716 líneas) contiene toda la lógica de la API (Axum), incluyendo:
- Rutas de autenticación (`/auth/register`, `/auth/login`)
- Gestión de elecciones (crear, listar, iniciar, cerrar)
- Whitelist para elecciones privadas
- Validación de identidad y votación
- Consultas de resultados y auditoría

## Análisis de Problemas Actuales
### 1. **Manejo de errores deficiente**
   - `unwrap()`/`expect()` en lugares críticos (líneas 92, 101, 152, 186, etc.)
   - Errores de base de datos convertidos a `String` sin contexto
   - Falta de errores estructurados (`ApiError` enum)

### 2. **Validación de entrada insuficiente**
   - `access_type` como `String` en lugar de enum (línea 114)
   - Fechas `start_date`/`end_date` no validadas (start < end)
   - Campos `form_config` JSON sin validar estructura
   - No se verifica longitud de username/password

### 3. **Problemas de seguridad**
   - Secreto JWT por defecto `"secret"` (línea 92)
   - `hash(payload.password, DEFAULT_COST).unwrap()` (línea 152) – costo podría ser configurable
   - `verify(payload.password, &pwd).unwrap_or(false)` (línea 186) – ignora errores de bcrypt
   - Identity token placeholder `"VALID_TOKEN_PLACEHOLDER"` (línea 422)
   - Firma de recibo placeholder `"ELECTION_SIGNATURE_PLACEHOLDER"` (línea 571)

### 4. **Acoplamiento alto y archivo extenso**
   - 716 líneas en un solo módulo
   - Mezcla de DTOs, handlers, lógica de negocio
   - Dificulta pruebas y mantenimiento

### 5. **Duplicación de código**
   - Consultas SQL similares repetidas (ej: obtener elección por ID)
   - Lógica de verificación de whitelist duplicada en `check_eligibility` y `validate_identity`

### 6. **Falta de transacciones**
   - `submit_vote` realiza múltiples inserts sin transacción (registro de nullifier + ballot)
   - Posible inconsistencia si falla el segundo insert

### 7. **Logging y trazabilidad ausentes**
   - No hay logs de acciones críticas (registro, votación, cierre de elección)
   - Difícil depuración y auditoría

### 8. **Estado de elección no verificado completamente**
   - `submit_vote` (línea 527) verifica existencia pero no si está `OPEN`
   - `start_election`/`close_election` no validan propiedad del admin

### 9. **Tipos no idiomáticos**
   - `access_type` como `String` en lugar de enum Rust
   - `status` comparado con strings literales en lugar de usar el enum de DB

### 10. **Falta de pruebas**
   - No hay pruebas unitarias de handlers
   - No hay pruebas de integración para flujos completos

## Mejoras Propuestas

### Prioridad Alta (Críticas para seguridad/estabilidad)
1. **Refactorizar manejo de errores**
   - Crear `ApiError` enum con variantes `Validation`, `Database`, `Auth`, etc.
   - Implementar `IntoResponse` para devolver respuestas HTTP consistentes
   - Reemplazar todos los `unwrap()`/`expect()` con `?` y mapeo a `ApiError`

2. **Validación de entrada robusta**
   - Crear `AccessType` enum (`Public`, `Private`) y usar en `CreateElectionRequest`
   - Validar `start_date < end_date`
   - Validar `form_config` con JSON Schema o estructura mínima
   - Validar longitud y complejidad de passwords

3. **Seguridad JWT y contraseñas**
   - Exigir `JWT_SECRET` en entorno, sin valor por defecto
   - Usar `bcrypt::hash` con costo configurable por entorno
   - Manejar errores de `bcrypt::verify` apropiadamente
   - Implementar token de identidad real (JWT firmado con nullifier)

4. **Transacciones de base de datos**
   - Envolver `submit_vote` en transacción SQL
   - Asegurar rollback si falla cualquier paso

5. **Verificación completa de estado**
   - En `submit_vote`, verificar que elección esté `OPEN` y no haya expirado
   - En `start_election`/`close_election`, verificar que el admin sea el propietario

### Prioridad Media (Mejoras de mantenibilidad)
6. **Dividir módulo en sub-módulos**
   - `src/api/auth.rs` – handlers y DTOs de autenticación
   - `src/api/elections.rs` – gestión de elecciones
   - `src/api/vote.rs` – votación y validación
   - `src/api/whitelist.rs` – lista blanca
   - `src/api/mod.rs` – reexportar y configurar router

7. **Extraer lógica común**
   - Crear `ElectionRepository` con métodos `find_by_id`, `is_whitelisted`, etc.
   - Crear `VoteService` para lógica de votación
   - Reducir duplicación de consultas SQL

8. **Implementar logging estructurado**
   - Usar `tracing` para eventos importantes
   - Loggear acciones de admin, votos, errores de validación

9. **Tipos fuertes para estados y accesos**
   - Crear `ElectionStatus` y `AccessType` enums que coincidan con los tipos PostgreSQL
   - Usar `sqlx::Type` para integración directa

### Prioridad Baja (Mejoras incrementales)
10. **Optimizaciones de rendimiento**
    - Usar `query_as!` para evitar `try_get` manual
    - Considerar paginación para `list_elections`

11. **Mejorar respuestas de error**
    - Mensajes de error más informativos pero no reveladores
    - Códigos de error consistentes

12. **Documentación de API**
    - Añadir doc comments para generación de OpenAPI
    - Considerar `utoipa` para documentación automática

### ApiError enum
```rust
#[derive(Debug)]
pub enum ApiError {
    Validation(String),
    Database(sqlx::Error),
    Auth(String),
    NotFound(String),
    Conflict(String),
    Internal(String),
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        match self {
            ApiError::Validation(msg) => (StatusCode::BAD_REQUEST, msg).into_response(),
            ApiError::Database(e) => {
                tracing::error!("Database error: {}", e);
                (StatusCode::INTERNAL_SERVER_ERROR, "Database error").into_response()
            }
            // ... otros casos
        }
    }
}
```

### Handler con transacción
```rust
async fn submit_vote(
    State(state): State<AppState>,
    Json(payload): Json<SubmitVoteRequest>,
) -> Result<Json<VoteReceipt>, ApiError> {
    let mut tx = state.db.begin().await?;
    
    // Verificar elección OPEN
    let election = sqlx::query_as!(Election, "SELECT ...")
        .fetch_optional(&mut *tx)
        .await?;
    
    // Registrar nullifier
    sqlx::query!("INSERT INTO voter_registry ...")
        .execute(&mut *tx)
        .await?;
    
    // Insertar ballot
    sqlx::query!("INSERT INTO ballots ...")
        .execute(&mut *tx)
        .await?;
    
    tx.commit().await?;
    
    Ok(Json(receipt))
}
```

## Conclusión
Las mejoras propuestas transformarán `src/api/mod.rs` de un prototipo funcional a una API de grado productivo, manteniendo los principios de seguridad y transparencia que definen SoleSigner. La implementación priorizada aborda primero los riesgos críticos (seguridad, manejo de errores) antes de refactorizaciones de mantenibilidad.
